# 底仓策略执行口径（以此为准）

这份文档专门用来固定 `list / guadao`、旧 `transfer` 和新 `profitTrade` 的业务含义，避免后续实现时再次理解反。

## 1. 两种策略的目的

### `transfer`

这里的 `transfer` 是历史执行器里的旧导余额做T链路，当前只作为兼容逻辑理解，不再作为新功能扩展方向。

- 目的：赚差价
- 核心判断：`transfer_real_ratio >= 阈值`
- 成本口径：`Steam 买入成本 = Steam 市价 × 0.73`
- 利润来源：`C5 卖出到手` 高于 `Steam 买入成本`

一句话：

- `transfer` 是低成本买 Steam，再高价卖 C5，吃价差

### `profitTrade`

- 目的：真正搬砖赚钱
- 核心判断：预期 ROI 达到阈值，且单件价值达到阈值
- 成本口径：`Steam 买入价 × guadaoMaxListingRatio`
- ROI 口径：`C5预计到手 / Steam买入价 - guadaoMaxListingRatio`
- 收入口径：
  - 当前 C5 在售价估算：`C5挂价 × 0.99`
  - C5 最近成交价：已按扣手续费后的到手价理解，不再二次乘 `0.99`

一句话：

- `profitTrade` 是新做T执行器，必须先锁定旧底仓 A，再买 Steam 替换资产 B，之后卖 A、记录收益。

### `list` / `guadao`

- 目的：导余额
- 核心判断：`listing_ratio <= 阈值`
- 核心不是赚差价，而是把库存价值换成 `Steam 余额`

一句话：

- `list` / `guadao` 是卖 Steam、补 C5，用更低损耗把货换成 Steam 余额

## 2. `transfer` 的正确执行含义

`transfer` 不是“买到的那件再拿去 C5 卖”。

正确含义是：

1. 用 `Steam 余额` 在 Steam 市场买入同类饰品
2. 在 C5 上卖出的，是原来底仓里已经有、且当前可交易的那件
3. 新买到的那件，是补回底仓/替换底仓的那件
4. 所以：
   - 卖的不是刚买的那件
   - 刚买的那件会进入冷却
   - 但这不影响把“原来的可交易底仓”立即拿去 C5 卖

## 3. `transfer` 的状态理解

从执行角度看：

1. `Steam` 先买
2. `C5` 立刻卖原底仓可交易资产
3. 卖出完成后，底仓实际由“刚买回来的冷却资产”顶上
4. 等这件 replacement 过冷却后，状态再回到正常 `holding`

也就是说：

- `transfer` 不需要等冷却以后再去挂 C5
- 需要等冷却的，是补回来的 replacement 资产，不是拿去卖的那件

## 4. 自动执行范围

自动执行时，只允许操作你上传了 `STEAM_COOKIES` 的那个 Steam 账号。

具体口径：

- 扫描库存：仍然可以读取 C5 绑定的全部账号，用来做全局判断
- 自动 `Steam` 买卖：只允许使用 `STEAM_COOKIES` 对应账号
- 自动 `C5` 卖出：只允许使用这个账号名下、当前可交易的底仓资产

不能做的事：

- 不能自动卖别的 C5 绑定账号的资产
- 不能把 `transfer` 里刚买到的那件，误当成 C5 卖出对象

## 5. 代码实现时必须满足

### `profitTrade`

- 必须先锁 A，再买 B；锁不到 A，禁止买 B。
- 初始锁 A 使用 `active + reserved_until`，默认短时间过期，防止扫描/审计阶段长期占用资产。
- 买 B 前必须重新读取 Steam `orderbook`，用当前卖家最低价走 `createbuyorder`，按实际付款价复算 ROI；低于 `profitTrade.minRoi`、价格移动超出容忍范围，或 A 锁已过期时禁止买入，并释放短期 A 锁、取消该笔买 B 前流水。
- 自动执行一轮必须连续完成 `发现机会 -> 审计通过 -> 锁定A -> 买入B -> C5上架`；`C5售出 -> 收益结算` 是等待 C5 后续成交的阶段，允许在之后轮次推进。
- 买 B 的 Steam 账号选择：优先使用 A 资产所属 Steam 账号；如果该账号余额不足，再从其他本地账号里选择“可用余额足够且余额最小”的账号。余额是否足够按 Steam 实际付款价判断，收益核算仍按 `Steam买入价 × guadaoMaxListingRatio`。
- Steam 买 B 成功后，A 的锁不能再按短期时间自动过期，应转成 `active + reserved_until=NULL`，直到 C5 上架成功或人工处理。
- A 一旦 C5 上架成功，锁不能释放，应该从 `active` 变成 `consumed` 或等价长期占用状态。
- C5 上架失败或状态不确定时，不能释放 A 锁；该笔流水应进入 `manual_required`，前端展示失败原因，等待人工处理。
- C5 售出检测当前按“本程序 productId 不再出现在 C5 在售列表”推进；没有 C5 成交详情 API 前，结算收益可以按本程序上架价估算，但必须在 `note.c5SoldNetPriceSource` 标明来源，不能伪装成官方成交明细。
- B 是否还在冷却，不阻塞本笔收益结算；后续库存刷新会自然把 B 纳回可用资产。
- `profitTrade` 和 `list / guadao`、旧 `transfer` 不能操作同一个 `asset_id`。
- 资产互斥以 `asset_reservations` 为准；挂刀和旧 `transfer` 选择本地可交易资产时必须跳过 active/consumed reservation。
- 每笔做T要写 `profit_trades` 流水，前端按步骤展示：`发现机会 -> 审计通过 -> 锁定A -> 买入B -> C5上架 -> C5售出 -> 收益结算`。
- 未来 AI 审计只能作为最终审计官，不能绕过硬规则、资产锁和收益阈值。

### `transfer`

- 先验证当前有“本账号、同品类、可交易”的旧底仓资产可卖
- 再执行 `Steam buy_listing`
- 再把“旧底仓资产”上架到 `C5 sale_create`
- 后续跟踪新买回来的 replacement 资产冷却状态

### `list` / `guadao`

- 继续走原来的：
  - `Steam` 卖
  - `C5` 补仓
- `guadaoMaxListingRatio` 只作为硬上限预筛；真实上架前必须按 Steam `orderbook` 重新计算当前执行挂价和 `listing_ratio`。
- 进入候选池后，不再计算额外的全局动态阈值；每个品种直接使用自己本轮实时算出来的 `listing_ratio`。
- 本轮新开挂刀按每个品种自己的实时 `listing_ratio` 从低到高执行；比例相同时，最近卖出更快的品种优先。
- 不按盘口数量分桶，不关心 Steam 墙里有多少个；每个候选只对应一个当前执行挂价和一个比例。
- 每笔新挂刀必须冻结开单时的比例字段，后续补仓优先用 `maxRebuyRatioAtOpen`，不能被之后的动态比例或当前全局配置影响；旧流水缺少该字段时才兼容使用当前 `guadaoMaxListingRatio`。

## 6. 一句总记忆

- `profitTrade`：新赚钱执行器，先锁 A，再买 B，卖 A，记录真实收益
- `transfer`：旧兼容链路，赚差价，买 Steam，卖 C5，卖的是旧底仓
- `list`：导余额，卖 Steam，补 C5


## 7. 废弃配置说明

- `rebuyBeforeListing` 已废弃，仅保留配置兼容。
- `--rebuy-first` / `--no-rebuy-first` 已废弃，仅保留命令行兼容。
- 当前执行顺序固定：
  - `transfer`：先 Steam 买，再 C5 卖。
  - `list / guadao`：先 Steam 卖，再 C5 买。

## 8. 当前执行注意事项

- `list / guadao` 的核心闭环是 `sell_on_steam -> rebuy_on_c5`，不要改成先补仓再卖出。
- `python main.py executor start --once` 会推进旧状态，再判断是否可以开启新动作。
- `list / guadao` 必须保留 `listing_pending`、`listed`、`pending_rebuy`、`rebuy_failed` 等状态边界。
- Steam Guard 自动确认只能确认本程序流水对应的 `asset_id`，不能全量确认当前账号的 mobile confirmations。
- Steam Guard 待确认、挂单消失、C5 暂时无货，都不能被粗暴当作状态异常。
- C5 补仓失败或余额不足时，按失败原因保留流水，不要通过重置数据库状态掩盖。
- `rebuyBeforeListing`、`--rebuy-first`、`--no-rebuy-first` 不再决定真实执行顺序。
