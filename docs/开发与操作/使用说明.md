crates_only（广义箱子模式；旧 case_only 自动兼容）
库存放箱子可交易资产：1件、5件。
预期：
1件 时最多上 1 条 [上架]。
5件 时最多上 5 条 [上架]（受 maxListPerCycle 限制）。
非箱子即使有库存也不应上架。
non_case_only（非箱子模式）
非箱子可交易资产分别做：0件、1件、5件。
预期：
0件：无上架，原因里应是无可执行候选或无可交易资产。
1件：上架 1 条。
5件：上架最多 5 条。
箱子库存不应被上架。
all（全模式）
场景A：有箱子，另有非箱子；分别做 1件、5件。
场景B：只留 1 个箱子；分别做 1件、5件。
场景C：0个箱子（只有非箱子）；分别做 1件、5件。
预期：
A：箱子和非箱子都可进入候选，最终上架数受 maxListPerCycle。
B：只会看到该箱子上架。
C：不会因“没箱子”卡住，非箱子照常上架。

Profit Trade 新前端和日志：

后端和前端仍然是两个进程，搬砖做T、C5扫货等页面共用同一个 Python API：

Vite 实际端口以终端输出为准。Profit Trade 三个路由：

- #/profit-trade/overview：S1 总览，保留进行中和已完结区域，并显示 ROI > 0 观察池。
- #/profit-trade/interruptions：S2 中断追踪。
- #/profit-trade/logs：S3 实时日志。

旧 #profit-trade 会跳到总览。API 未启动时页面只显示离线/空状态，不读取静态 dashboard 文件冒充当前真实数据。

Profit Trade 扫描和收益口径：

- scanMaxItems / --scan-max-items 只为旧配置和调用兼容保留，不再截断扫描。
- 所有通过可交易、保护和 minItemValue 前置过滤的品类都会读取 Steam orderbook、计算 ROI 和执行 C5 风控。
- limit 只限制最后返回或记录的执行机会数量。
- ROI = C5挂价 / Steam买入价 * 0.99 - profitTrade.balanceDiscount。
- 真实成本 = Steam买入价 * profitTrade.balanceDiscount。
- 不使用 common.balanceDiscount，也不跟随 guadaoBalance.guadaoMaxListingRatio。
- ROI > 0 观察池只保存观察数据和历史，不等于可执行机会，不会锁 A、买 B 或上架 C5。

S2 的“知晓并隐藏”只折叠默认显示，不删除流水、时间线或日志，可以恢复。关联 Steam buy order 未确认终态、无订单 ID 的不确定买入或证据冲突时，后端会拒绝直接隐藏，必须先安全确认远端终态。

S3 只读取 source=profit_trade 的 Steam、C5 和 local 活动，不包含上面的挂刀 executor.log，也不包含 C5 扫货。Profit Trade 结构化日志自动写入：

logs\profit_trade\YYYY-MM-DD.jsonl

日志按 UTC 自然日切分，闭日压缩成 .jsonl.gz，默认保存 90 天。页面可以实时查看、按时间/交易筛选，并下载 JSONL 或可读 .log。Cookie、sessionid、密码、API key、Steam Guard/identity/device secret、C5 app-key、trade URL、token/styleToken 和完整认证请求体不会保存。

429 会记录 request ID、账号、Steam operation、状态码、耗时、Retry-After 和近期 Profit Trade 请求频率，但日志本身不改变现有重试或 relogin 规则。429 不等于 cookie 失效；仅靠 Profit Trade 日志也不能证明是挂刀执行器导致，需要以后用独立挂刀日志按 UTC 时间和账号对照。
